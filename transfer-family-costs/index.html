AWS Transfer Family · 30-day analysis · 2026-05-15

One unused SFTP server is costing $216/month. Deleting it cleanly is a five-step job.

99.7% of the Transfer Family bill is per-endpoint ProtocolHours, not data. The account runs two SFTP servers: EmpowerFreshProFTP is doing real work every minute of every day, and EmpowerFreshDeliveryFTP hasn't seen a legitimate session since November 2024 — only internet brute-force scanners hit it now.

The recommendation in one line

Delete CloudFormation stack EmpowerFreshDeliveryFTP. It owns the unused SFTP server and every supporting resource that's specific to it — Route53 record, API Gateway identity provider, identity Lambda, IAM roles, and log groups. Three things survive the stack delete and need a separate decision: the underlying S3 bucket empowerfresh.ftp-test (still receiving non-SFTP writes), any Secrets Manager entries with prefix SFTPDelivery/*, and an orphaned ACM certificate that was attached outside the stack.

Why this is safe

  • Zero legitimate SFTP sessions in 30 days. Last real session: 2024-11-07, two days after the server was created.
  • No code in any local repo connects to the delivery SFTP hostname, server ID, or API Gateway. The only references are to the underlying S3 bucket — which survives stack deletion.
  • The active prod server (EmpowerFreshProFTP) is a separate stack with a separate identity provider, separate IAM roles, and a separate S3 bucket. The two are not coupled.
  • Removal is fully reversible: the CloudFormation template lives in EmpowerFresh-CloudFormation/ECS/EmpowerFreshDeliveryFTP/ and can be re-deployed end-to-end in minutes.
Bill anatomy

It's not data. It's the endpoints.

Transfer Family charges $0.30/hour per active SFTP/FTPS endpoint — about $216/month per server, on whether anyone connects or not. Two endpoints × 24 × 30 = 1,440 protocol-hours. Data transfer and connector calls together come to under $2/month.

Why endpoint hours dominate

Transfer Family endpoints have minimum 1-hour billing granularity. There's no scale-to-zero and no idle discount. A server that handles one upload per day costs the same as one that handles a thousand. That makes endpoint count — not throughput — the only knob that matters.

For low-frequency outbound-only flows there's a much cheaper alternative: SFTP Connectors bill per-call ($0.001/call + bytes). Your existing 616 connector calls last month cost $0.61 total. For comparison, the connector path would need to make ~216,000 calls in a month to cost what one always-on endpoint costs.

Step 1 of 5

Pre-flight checks

Confirm with your own eyes that nothing is connecting to the delivery server before changing anything.

1.1 · Confirm zero recent sessions

Show that the last 30 days of session events in the user-session streams are empty (only the ERRORS stream should have data). If anything besides ERRORS has events newer than a few months, stop and investigate.

# Most recently active log streams on the delivery server
aws logs describe-log-streams \
  --profile claude --region us-east-1 \
  --log-group-name /aws/transfer/s-6eb74dd6520446a1b \
  --order-by LastEventTime --descending --max-items 10 \
  --query 'logStreams[].[logStreamName,lastEventTimestamp]' --output table

Expected: only ERRORS has a recent timestamp; every other stream is dated 2024.

If the list is short and you recognize every username, you're safe to delete them in step 4. If anything looks unfamiliar, pause.

1.4 · Check the S3 bucket

The bucket empowerfresh.ftp-test is not deleted by the stack. It also still receives writes from non-SFTP paths (a recent April 2026 invoice batch landed under russdavis/gohugos/Invoice/). Confirm:

aws s3 ls s3://empowerfresh.ftp-test/ --profile claude --recursive --summarize | tail -30

Decision needed: leave the bucket alone (cheapest, simplest) or migrate the recent contents elsewhere and decommission the bucket in a follow-up. The bucket decision is independent of the SFTP server decision.

1.5 · Note the orphan ACM certificate

The Transfer server has an ACM certificate attached (arn:aws:acm:us-east-1:061051251509:certificate/8eb9871d-…) even though SFTP doesn't use it (certs are for FTPS/FTP). The cert was added outside CloudFormation and will not be deleted with the stack. ACM certs are free to keep, but you can delete the orphan in step 4.

Step 2 of 5

Disable the server and wait

A reversible dry run. Take the endpoint offline for a few days; if anyone or anything was secretly depending on it, they'll complain. Cost continues during the wait — endpoint-hours still bill while OFFLINE — but this is the safety net.

2.1 · Stop the server

aws transfer stop-server \
  --profile <your-profile> --region us-east-1 \
  --server-id s-6eb74dd6520446a1b

The state goes ONLINE → STOPPING → OFFLINE. New connection attempts will fail with a TCP-level reject; existing sessions terminate. No data is touched.

2.2 · Confirm it's offline

aws transfer describe-server \
  --profile <your-profile> --region us-east-1 \
  --server-id s-6eb74dd6520446a1b \
  --query 'Server.State'

Expected: "OFFLINE".

2.3 · Wait 3–7 days

A week is generous given there are no legitimate users to begin with, but covers weekly batch jobs. Set a calendar reminder. During the wait:

  • Watch the ERRORS stream — failed-auth scanner traffic will continue and is expected. Anything new from an internal IP would be a red flag.
  • Watch for support tickets, Slack mentions, or PagerDuty alerts that name "delivery FTP" or ftp.empowerfresh.delivery.
  • If anything comes up, start-server reverses this step immediately.

2.4 · Re-enable (rollback) if anything breaks

aws transfer start-server \
  --profile <your-profile> --region us-east-1 \
  --server-id s-6eb74dd6520446a1b

3.2 · Run the delete

# Snapshot the template first so re-creation stays trivial
aws cloudformation get-template \
  --profile <your-profile> --region us-east-1 \
  --stack-name EmpowerFreshDeliveryFTP > /tmp/EmpowerFreshDeliveryFTP.template.json

aws cloudformation delete-stack \
  --profile <your-profile> --region us-east-1 \
  --stack-name EmpowerFreshDeliveryFTP

aws cloudformation wait stack-delete-complete \
  --profile <your-profile> --region us-east-1 \
  --stack-name EmpowerFreshDeliveryFTP

There is already a Delete-EmpowerFreshDeliveryFTP.sh in EmpowerFresh-CloudFormation/ECS/EmpowerFreshDeliveryFTP/ that runs the equivalent command. It's a one-liner that calls delete-stack.

Step 4 of 5

Clean up orphans

Three things survive the stack delete and need a separate touch. None of them are billing in any meaningful way — this step is hygiene, not cost.

4.1 · Secrets Manager · SFTPDelivery/*

The identity-provider Lambda is gone, so these secrets are unreachable, but they still exist. Decommission them — Secrets Manager bills $0.40/secret/month and credentials shouldn't outlive the service that used them. Use --recovery-window-in-days 7 so you can recover if a name turns out to still be referenced.

# Get the list
aws secretsmanager list-secrets \
  --profile <your-profile> --region us-east-1 \
  --filters Key=name,Values=SFTPDelivery \
  --query 'SecretList[].Name' --output text

# Delete each (7-day recovery window)
for s in $(aws secretsmanager list-secrets \
    --profile <your-profile> --region us-east-1 \
    --filters Key=name,Values=SFTPDelivery \
    --query 'SecretList[].Name' --output text); do
  aws secretsmanager delete-secret \
    --profile <your-profile> --region us-east-1 \
    --secret-id "$s" --recovery-window-in-days 7
done

4.2 · Orphan ACM certificate (optional)

ACM certs are free to keep, but the cert attached to the deleted server is now unused. Cert ARN: arn:aws:acm:us-east-1:061051251509:certificate/8eb9871d-6ec5-4bde-81af-9d051aaf1ed6.

# Confirm nothing else uses it
aws acm describe-certificate \

  --certificate-arn arn:aws:acm:us-east-1:061051251509:certificate/8eb9871d-6ec5-4bde-81af-9d051aaf1ed6 \

# If InUseBy is empty, delete
aws acm delete-certificate \
  --profile <your-profile> --region us-east-1 \
  --certificate-arn arn:aws:acm:us-east-1:061051251509:certificate/8eb9871d-6ec5-4bde-81af-9d051aaf1ed6

4.3 · S3 bucket empowerfresh.ftp-test · decide separately

Three options, in order of safest → most aggressive:

  • Leave it. Cheapest path. Storage costs are pennies (576 KB total at last check). Some non-SFTP code (the SK CLI move tool) still references it as a destination.
  • Lifecycle-policy old content to Glacier. If you want to keep historical files reachable but stop them appearing in active inventories.
  • Migrate + delete the bucket. Move the April 2026 invoice files (russdavis/gohugos/Invoice/*) to wherever they belong long-term, remove the bucket from the SK CLI menu (EmpowerFresh-SK/cli/utils.ts:159,178), then empty and delete the bucket.

Recommendation: leave the bucket alone for now. It's $0/month in practice. Bucket cleanup is a separate decision that doesn't need to gate the SFTP-server savings.

4.4 · Archive the CloudFormation template directory (optional)

Move EmpowerFresh-CloudFormation/ECS/EmpowerFreshDeliveryFTP/ into an archive/ sibling so it's clearly historical, or leave it for reproducibility. Either is fine.

Safety net

Rollback plan

Every step is reversible; the further along, the more work the reversal is.

If you regret it before step 3

The server is just OFFLINE. One command brings it back:

aws transfer start-server \
  --profile <your-profile> --region us-east-1 \
  --server-id s-6eb74dd6520446a1b

If you regret it after step 3

The stack is gone — but the template is in source control and the snapshot you took in step 3.2 is on disk. Redeploying takes one command:

cd ~/Git/EmpowerFresh-CloudFormation/ECS/EmpowerFreshDeliveryFTP/
./Create-EmpowerFreshDeliveryFTP.sh

Caveats: the new server will get a new ServerId (so anything that hardcoded s-6eb74dd6520446a1b would need updating — we confirmed none does). The Route53 record points to a new hostname target managed by the new stack. The Secrets Manager entries you deleted in step 4.1 need to be recreated for any users — restore from the 7-day recovery window with restore-secret, or recreate from a password manager.

If you regret it after step 4

Secrets in their 7-day recovery window can be restored:

aws secretsmanager restore-secret \
  --profile <your-profile> --region us-east-1 \
  --secret-id SFTPDelivery/<username>

After the 7-day window closes, secrets are unrecoverable. That's a feature, not a bug — but it's why this guide uses the 7-day recovery window, not immediate force-delete.
